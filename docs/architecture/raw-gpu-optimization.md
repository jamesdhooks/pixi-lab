# Raw GPU optimization contract

Raw WebGL simulations should make the GPU do the work whenever the data model allows it. CPU code is acceptable for sparse topology decisions, pointer handling, settings, and one-time seed generation, but dense per-pixel or per-particle simulation should live in GPU passes.

## Required debug taxonomy

Every raw simulation `getDebugStats()` should expose these fields:

- `simulation`: short label for where the simulation work happens.
- `rendering`: short label for the renderer path.
- `gpuSimulated`: `true` when dense simulation state advances on the GPU.
- `gpuRendered`: `true` when final scene drawing is WebGL/GPU driven.
- `cpuTopology`: `true` when the CPU still owns sparse graph/body/topology decisions.
- `cpuUpload`: `true` when the scene performs recurring CPU-to-GPU state uploads.

Use `rawGpuMetricsToDebugStats()` for texture ping-pong GPU simulations. Use `rawUploadDebugStats()` only for legacy/internal CPU-upload field painters; it should not be the default for new simulations.

## Preferred patterns

- Dense fields: use render-target ping-pong textures and fragment shader passes.
- Dense particles: store state in textures and update through GPU passes.
- Sparse graphs: let CPU choose topology, then render with instanced GPU geometry.
- Sparse graph renderers should write directly into packed typed buffers when possible; avoid object segment arrays that are immediately repacked for WebGL uploads.
- Packed segment renderers should reuse endpoint and style buffers independently when multiple passes share geometry. For example, glow and solid branch passes should not upload identical segment endpoints twice.
- Only skip segment uploads when no later pass can overwrite the renderer's segment buffer. If different geometry families are drawn in the same frame, give them separate renderer/buffer owners before relying on revision-tracked upload skips.
- Sparse CPU-topology scenes should track geometry/style revisions. Upload static endpoints only when topology or layout changes, and upload dynamic style channels only when simulation values changed.
- Append-only sparse topology growth should use range uploads for new segment tails. Full endpoint uploads are still required after resize, reset, compaction, or GPU buffer capacity growth.
- Sparse graph style changes should dirty-track style ranges independently from geometry ranges. Local feed/prune/growth interactions should upload only the affected branch style span; full style uploads are reserved for resize, reset, capacity rebuild, palette/style invalidation, or global simulation scans.
- Dirty style ranges should have a direct packed-index-to-model lookup. Avoid walking every model node to repack a small dirty upload span; the CPU packing work should scale with the dirty range, not total graph size.
- Sparse growth/topology models should maintain active candidate index lists incrementally. Avoid rebuilding tip/frontier lists by scanning the full graph inside every growth event.
- Packed sparse graph render bridges should cache segment counts. If geometry and style revisions are unchanged, marker-only updates should not walk the full graph just to rediscover draw counts.
- Saturated sparse growth scenes may throttle style/energy scans when interactions are idle and topology cannot grow. Batch the effective delta instead of changing total simulation time, budget graph maintenance into chunks, scale each chunk's effective delta so every node receives elapsed time over a full scan cycle, and expose skipped scans plus scan start/count/total/effective-dt in debug stats.
- Sparse GPU-rendered scenes may skip clears/uploads/draws on identical settled frames if the previous framebuffer remains valid. They must force redraw on resize, reset, settings/style changes, and pointer interaction, and expose skipped draw frames in debug stats.
- Prefer the raw host `shouldRender` gate for truly idle raw scenes. The host accumulates skipped delta and passes it into the next render callback, so throttled simulations preserve elapsed simulation time instead of silently slowing down.
- Raw host render gates should clear pending render delta on reset and expose skipped-frame/pending-delta telemetry so idle behavior can be audited without a profiler.
- Empty particle scenes should use the host render gate when not in demo/autoplay mode. Force redraw on reset, settings/style/mode changes, pointer input, particle creation/removal, and transient effects.
- Particle and constraint scenes should use the host render gate for empty non-demo states and for solver-settled states reported by `AdvancedCircleParticleEngine.isAwake` or `AdvancedCollisionStressEngine.isAwake`. Wake the shared solver on topology edits, particle creation, pointer forces, bounds changes, and meaningful constraint-setting changes. Do not skip active solver frames just because the last GPU upload was clean.
- Sleep-gated particle scenes should expose whether the current state is eligible for the sleep render gate. This makes idle savings distinguishable from accidental starvation when reading debug stats.
- Soft bodies and constraint particles: keep solver data in typed arrays, upload active ranges only, and render as instanced/skinned geometry.
- Solver-owned state packing: CPU solvers that seed GPU textures should expose writer helpers for position, velocity, attribute, and constraint channels. Scenes should not duplicate texture-channel packing loops.
- Solver stats used by GPU sync/debug paths should be maintained incrementally. Avoid scanning all active particles for counts on every stats read or settings clamp.
- Soft-body visual skins: prefer GPU density/metaball compositing over CPU-built triangle skins when the visual result can be derived from particle centers.
- Uniforms: cache locations and reuse typed arrays for palette, emitter, and interaction data.
- Buffers: grow capacity geometrically, then upload active float ranges with `bufferSubData`.
- Instanced particle renderers should split dynamic channels from static channels when practical. Positions usually change every frame; radius, seed, material, group, or local id should upload only when the active particle set changes.
- Static instanced particle channels should support range uploads. When active particle count grows, upload only the newly appended static attributes; fall back to full-range upload when particles are compacted, removed, or otherwise reordered.
- Static channel range uploads need explicit invalidation keys for settings-driven changes. If radius, material, seed mapping, grouping, or palette-dependent static data changes, mark the static buffer dirty and force a full active-range upload.
- Debug stats should report measured active upload counts when render helpers can return them; avoid capacity-based or stale estimates for optimized GPU paths.
- GPU render helper stats should separate draw counts from upload counts. Reuse-heavy paths should be able to prove they drew existing GPU buffers while uploading zero or near-zero floats.
- Shared GPU render helpers may bind their own programs, framebuffers, textures, vertex arrays, and blend state. Scene render paths that draw additional passes afterward must explicitly restore the next pass state instead of assuming the previous scene-local program or VAO is still bound.
- Texture-backed simulations should separate one-time or topology-edit seed upload metrics from per-frame upload metrics. A scene can have seed upload cost without recurring `cpuUpload: true`.
- Texture-backed preview/demo scenes should expose seed upload telemetry in debug stats whenever the shared GPU state container can measure it.
- Texture-backed constraint scenes should dirty-track dynamic seeds separately from topology seeds. Creating GPU containers should mark them dirty, but actual uploads should happen at a single explicit sync point so preview/demo activation does not double-upload identical state.
- Live CPU-owned constraint scenes may use texture-backed GPU density rendering as an interim bridge. In that mode, upload active CPU particle state into `RawGpuConstraintParticleState`, avoid CPU-expanded density-center geometry, and report the live texture path separately from full GPU simulation.
- Debug stats must distinguish GPU-authoritative simulation from GPU render bridges. A live constraint scene that uploads CPU-solved positions into GPU textures is `gpuRendered: true` but not `gpuSimulated: true`; expose bridge flags such as `liveGpuRenderBridgeOnly` until the GPU state becomes authoritative.
- Live CPU-to-GPU texture bridges should split dynamic and static texture uploads. Positions and velocities may update every rendered frame, but attributes, constraints, neighbor slots, radius/material data, and topology should upload only on creation, reset, settings invalidation, or topology edits.
- Render-only texture bridges should upload only the channels consumed by the renderer. Density/metaball renderers that read position plus attributes should use dynamic position uploads plus attribute-only static uploads, and should skip velocity uploads until a GPU simulation pass needs that velocity texture.
- Static particle attribute uploads should support row-covered range uploads for append/shrink topology changes. Use full active attribute uploads only for reset, settings invalidation, capacity rebuild, or static-data remapping; append-heavy streams should upload only the newly affected attribute rows.
- CPU staging writers should mirror GPU range uploads. If a bridge uploads a static attribute range, it should repack only that range in the staging buffer instead of rewriting all active static attributes first.
- Debug stats for texture bridges should expose static staging write counts and upload mode separately from GPU upload floats. This proves CPU packing work shrank along with GPU bandwidth, and makes full rebuilds distinguishable from append/shrink range updates.
- Sparse topology renderers such as Vascular should expose geometry and style upload modes separately. Growing append-only geometry should report `append-range` rather than `full`, while animated style/energy updates should report whether the renderer used a full style upload or a dirty style range.
- Circle-only collision scenes that still require a CPU solver should bridge live rendering through `RawGpuConstraintParticleState` plus `RawGpuConstraintParticlePointRenderer` before adding a scene-specific instanced fallback. Recurring uploads should be position-only; radius/seed/inverse-mass attributes should upload only on creation, reset, settings invalidation, or active-count shrink/growth.
- Scene code that creates, deletes, rebuilds, or fixture-edits constraint topology should call a shared dirty helper rather than directly flipping individual seed booleans. This keeps preview/demo and future live GPU modes on the same sync contract.
- GPU seed uploads should skip ping-pong write targets when the next GPU pass overwrites them before rendering or reading. Keep write-target uploads as the conservative default for paths that render immediately after seeding.
- Texture upload helpers must reuse scratch padding buffers for partial seeds. Do not allocate full-size temporary `Float32Array` buffers inside recurring `texSubImage2D` paths.
- Active-row texture uploads should use WebGL2 source-offset `texSubImage2D` directly when the stable source array contains the active row span. Scratch padding is a fallback for undersized seed buffers only; debug stats should make direct vs padded upload work visible. `RawGpuConstraintParticleState` is the source of truth for particle/constraint active, uploaded, and reserved row telemetry; scenes should prefer the helper-reported rows over recomputing row counts locally.
- Constraint neighbor-slot textures follow the same active-row upload rule as particle state textures. Topology seed uploads should use active rows and direct source-offset uploads from stable neighbor-slot buffers; padded scratch uploads should be visible and rare. The shared neighbor-slot helper owns shrink clearing: active uploads should cover the current active rows plus the previously resident row span that may contain stale slot data, then report active/uploaded/reserved rows.
- Constraint neighbor-slot textures should also support row-covered range uploads for dirty endpoint topology changes. Use full active topology uploads for reset, settings invalidation, capacity rebuild, or unknown graph rewiring; use range uploads only from solver-reported dirty endpoint spans, because adding a new link can change an older parent particle's neighbor slot.
- Constraint scenes should expose neighbor-slot CPU staging counts and topology range start/count separately from neighbor texture upload floats. A range texture upload is not the same as range CPU topology packing unless the writer also avoids walking/rebuilding unchanged slots.
- Dirty endpoint topology writers should keep per-particle constraint adjacency so range staging is truly local. The dirty-range writer should clear only the affected particle rows and walk only those particles' incident constraints; scanning the full link graph before a range texture upload defeats the point of the optimization.
- Texture-backed particle seed uploads should be active-row aware. Upload enough rows to cover the current active count and any previously uploaded active count that must be cleared, rather than uploading full stress capacity every topology edit.
- CPU writers feeding active-row texture uploads should clear and repack only the same active/previous-active range that will be uploaded. Avoid clearing full reserved capacity before a partial `texSubImage2D`.
- Sorted candidate telemetry states should not clear or upload their full reserved particle capacity when every downstream pass receives an explicit active `particleCount`. Clearing/uploading unused texels is only required when stale texels can be sampled by a pass that lacks active-count bounds.
- Texture-backed particle renderers should accept an active particle count. Draw full reserved capacity only for deliberate full-capacity stress clouds; topology-driven scenes should render the active count seeded into the GPU state.
- Live texture bridges should allocate GPU state capacity around active particle counts and grow geometrically with headroom. Reserve full stress capacity only for deliberate demo/stress clouds that label themselves as full-capacity work.
- Adaptive live GPU capacity should use shrink hysteresis. Grow promptly when active count needs more texture space, but do not shrink/recreate GPU state unless active demand falls well below the current allocation.
- This adaptive-capacity rule applies to point-render bridges and density/metaball constraint bridges alike. Live Snakes, Soft Bodies, and Ball Pit should not reserve solver max capacity unless the mode is explicitly a stress/demo cloud.
- Texture-backed particle simulation passes should accept the same active particle count as renderers. Full-capacity fragment work is appropriate only for deliberate full-capacity stress clouds.
- Texture-backed particle simulation passes should reduce viewport/work rows to the active row count when inactive texels are not consumed later. Uniform early-outs alone still pay full fragment cost.
- Debug stats for active-count GPU paths should expose active rows, uploaded rows, reserved rows, and active/capacity ratio so capacity-wide regressions are visible without profiling tools.
- GPU density/metaball renderers should report active point draw counts when they consume texture-backed particle state. This keeps visual splat work comparable with step/Jacobi pass telemetry.
- GPU point renderers should also report active point draw counts. Full-capacity stress scenes should expose those counts so intentional stress work is distinguishable from accidental capacity-wide rendering.
- GPU pass and renderer telemetry must reset to zero when work is skipped. Stale counters are worse than missing counters because they hide idle or inactive optimized paths.
- Full-capacity stress clouds, such as Ball Pit GPU demo modes, should label themselves explicitly in debug stats. They may intentionally pass full capacity to seed, step, and render calls, but that choice should be visible as `fullCapacityStressCloud` or equivalent telemetry before adding collision passes.
- If a scene has non-interactive preview/autoplay/demo modes, those modes should prefer texture-backed GPU simulation even when fully interactive play still uses a CPU solver. This applies to collision piles and constraint-particle demos alike.

## CPU constraint solver boundary

Ball Pit, Snakes, and Soft-Body Blobs currently use CPU solvers because their interactions depend on mutable topology, pointer picking, static fixtures, and constraint graphs. This is acceptable only as an optimized interim layer:

- Solver state must stay in typed arrays, not object graphs.
- Broadphase must avoid duplicate pair enumeration.
- Stats must be maintained incrementally when possible, not recomputed by scanning hot arrays every frame.
- Renderer uploads must use active ranges directly; do not allocate `.subarray()` views.
- Rendering must remain GPU-native, preferably instanced or skinned geometry.

The long-term GPU migration path is a shared constraint-particle backend with texture-backed position, velocity, radius, inverse-mass, and group/local-id state. CPU topology can seed or edit those textures, but dense integration, broadphase-friendly collision passes, and high-count stress modes should move to GPU render-target passes when the simulation no longer needs exact CPU-side pair identity.

Ball Pit GPU collision should be implemented as a shared dense circle-particle path, not as a scene-only shader. The required boundary is: texture-backed position/velocity/attribute state, a GPU broadphase or spatial-bin approximation that avoids all-pairs work, one or more collision-relaxation passes that preserve radius and inverse-mass semantics, and renderer consumption directly from the post-solve textures. Until that exists, full-capacity Ball Pit GPU demos are useful as render/integration stress clouds but must not be described as collision-complete.

`RawGpuParticleState` is the lightweight ping-pong position/velocity texture state for field-like particle simulations such as Space Debris. `RawGpuConstraintParticleState` is the shared memory contract for constraint-particle migration. It owns ping-pong position and velocity textures plus static particle-attribute and constraint textures. Use these shared containers for new high-count stress modes before adding scene-specific GPU state containers.

`RawGpuConstraintParticleStepPass` is the shared first-stage GPU integrator for that state. It advances positions and velocities, applies damping and speed limits, and handles rectangular bounds without recurring CPU uploads.

`RawGpuConstraintParticlePointRenderer` draws directly from those state textures using `gl_VertexID` texture fetches. Use it when a stress mode can render circles/points without reading positions back to the CPU.

`RawGpuConstraintParticleDensityRenderer` splats texture-backed particle state into a density target without CPU position uploads. Feed that density target into a metaball/composite pass when Snakes, Soft-Body Blobs, or high-count particle clouds should render as continuous bodies.

`RawGpuConstraintParticleJacobiPass` is the shared GPU distance-constraint primitive. It uses a gather/Jacobi layout: CPU topology seeds bounded per-particle neighbor-slot textures, then repeated relaxation passes run on the GPU without scatter writes or CPU readback. Prefer this for Snakes first, then Soft-Body Blob boundary/interior constraints.

`RawGpuConstraintParticleCircleCollisionPass` is the shared migration point for GPU circle-particle collision. Its local-texture-neighborhood implementation establishes the pass contract, active-row telemetry, ping-pong state ownership, configurable relaxation iterations, and cross or 3x3/Moore texel-neighborhood sampling. It can also consume bounded spatial neighbor-slot textures seeded from CPU topology as an intermediate bridge. Production Ball Pit collision still requires a GPU-owned spatial-bin or tiled-neighborhood backend before replacing the CPU broadphase.

`RawGpuConstraintParticleGridKeyPass` is the first reusable GPU-owned broadphase stage for constraint particles. It reads particle position textures and writes a per-particle grid-key texture containing cell coordinates, linear cell id, and enabled state. It reports `broadphaseOwner: 'gpu'` but `producesCandidateSlots: false`; do not treat it as an authoritative collision broadphase until a follow-up GPU candidate/scatter pass consumes those keys and reports slot overflow/completeness telemetry.

`RawGpuConstraintParticleCandidateSlotPass` consumes the grid-key texture and writes the existing neighbor-slot texture format from GPU state. Its initial backend is `gpu-grid-key-window`: it filters a bounded texture-window neighborhood by grid cells, which is useful for exercising the GPU candidate path and avoiding CPU uploads in preview/demo stress modes. It is not spatially complete and must not be used as an authoritative dense collision backend until replaced or extended with a true GPU spatial-bin scatter/sort/tiled pass.

Candidate-slot stats must name their coverage and required replacement. `gpu-grid-key-window` reports `coverage: 'texture-window'`, `limitation: 'samples-adjacent-texture-neighbors-only'`, `requiredReplacement: 'gpu-spatial-bin-scatter-or-sort'`, and `suitableForAuthoritativeCollision: false`. Scenes should display these values in debug stats instead of inferring readiness from slot capacity alone. The next reusable backend should generate candidate slots from a world-cell resident list, not from nearby texture indices.

`RawGpuConstraintParticleSortedCellCandidatePass` is the next bridge backend. It consumes sorted particle state, grid keys, and a cell-range texture where each world cell stores `[start, end, count, enabled]` into the sorted particle texture. It then writes neighbor-slot textures by scanning resident particles in the 3x3 world-cell neighborhood instead of nearby texture indices. This can report `coverage: 'bounded-world-cell-residents'`, but its ownership is `hybrid` until the sort/cell-range construction happens on GPU. It is suitable for authoritative collision only when the resident scan limit covers the maximum cell occupancy and the output slot count covers all scanned resident slots; otherwise it remains a bounded migration probe.

Ball Pit live telemetry wires this backend through a separate sorted GPU state and `RawGpuConstraintParticleCellRangeBridge`, which owns the CPU-built cell-range texture. That path is intentionally sampled and labeled `hybrid-sorted-cell-candidate-copy`: the shader-generated candidate slots now come from world-cell residents, but particle sorting and cell-range construction are still CPU bridge work. This bridge is the reusable interim broadphase path for Ball Pit, Snakes, and Soft Bodies until the range construction is replaced with a GPU-owned sort/scatter pass.

`RawGpuConstraintParticleCellRangeBridge` must stay row-windowed while it exists. It reports `activeRows`, `uploadedRows`, `reservedRows`, `uploadRowStart`, `activeCellStart`, and `activeCellCount` so scenes can prove the CPU fallback is only clearing and uploading the rows touched by the current sorted-cell range plus the previous resident span needed to clear stale cells. A full `width * height * 4` upload from this bridge is now a regression unless the active cells genuinely span the full range texture; the preferred endpoint remains GPU-owned sorted-key-range derivation with zero bridge upload floats.

Snakes use the same bridge in their live enhanced render telemetry. The scene can now use original-index resident-list candidate slots for the live GPU render collision bridge on frames where the resident-list candidate pass was freshly sampled and reports authoritative broadphase coverage. Otherwise it falls back to CPU spatial neighbor slots. Snakes also run a non-authoritative batched collision stress solve over the sorted candidate copy and report whether every generated slot was consumed. Preview/demo paths keep the constraint-particle state resident after seeding and label the step source as `persistent-gpu-step-probe`; interactive live paths still label CPU-seeded bridge work and expose `liveGpuDynamicUploadSkipBlocker` instead of silently diverging from the CPU-owned solver. This is the migration checkpoint before replacing the CPU-owned constraint solver and topology model.

Soft Body Blobs now sample the same sorted-cell bridge against their CPU grid/contact solver, and can route non-authoritative contact, viscosity, pressure, and body-shape stress passes through original-index resident-list candidates when that fully GPU-owned broadphase reports complete coverage. The viscous body, area preservation, settling, and skin topology remain CPU-authoritative, but debug stats expose whether stress came from `gpu-resident-list` or the older `gpu-sorted-cell-ranges` fallback, plus candidate coverage, occupancy, upload cost, pass consumption, and offscreen gather cost beside the existing CPU grid pair checks. Like Snakes, preview/demo blobs can keep GPU state resident after the seed upload while live play reports the precise blocker preventing dynamic upload elimination. This is the checkpoint before replacing CPU grid loops with GPU-friendly soft-body contact, viscosity, and area kernels.

Snakes and Soft Body Blobs should split `cpuUpload` into actionable migration buckets the same way Ball Pit does. `liveGpuDynamicCpuUploadEliminated` identifies frames where the live texture state is resident, while `liveGpuRemainingCpuBridgeUploadFloats`, `liveGpuRecurringCpuBridgeUploadFloats`, `liveGpuSeedCpuBridgeUploadFloats`, and `liveGpuRemainingCpuBridgeBlocker` identify whether the remaining CPU-owned bridge is dynamic seeding, topology-neighbor seeding, CPU spatial-neighbor slots, CPU sorted-candidate copies, cell-range bridge uploads, index-map bridge uploads, or body-metadata bridge uploads. Optimization decisions should prioritize recurring bridge upload cost; seed/static upload cost is still useful for reset/topology churn but should not be treated as a steady-state hot-path bottleneck. This keeps constraint-scene optimization comparable with Ball Pit and prevents `cpuUpload: true` from hiding which bridge still needs to move to GPU.

Sorted-cell candidate generation can produce more neighbor-slot textures than the current circle-collision shader consumes in one solve. `RawGpuConstraintParticleCircleCollisionPass` currently reads at most eight neighbor textures per pass, while a 3x3 resident scan may require `residentScanLimit * 9` slots. Candidate stats must expose `collisionConsumableSlotCount`, `collisionRequiresBatchedSolve`, and `collisionRequiredBatches`; collision stats must expose provided versus ignored neighbor slots. Do not wire sorted-cell candidates into authoritative collision until either batched solves cover every generated slot or the collision shader is upgraded to consume the full resident-slot set safely.

Sorted-cell candidate slots are index-space local to the sorted candidate copy that generated them. Do not feed those slots into an unsorted live particle state; either solve/render against the same sorted state or add an explicit sorted-to-original index remap pass. Until that remap exists, Ball Pit and Snakes keep the sorted-cell solve as telemetry/stress on the sorted copy while the visible live solver remains CPU-authoritative.

`RawGpuConstraintParticleIndexMapBridge` is the remap bridge for the next stage. It uploads an `original index -> sorted texel` float texture from each sorted candidate copy, allowing a future fullscreen gather pass to write unsorted live particle texels by sampling solved sorted-state positions. When the sorted key array encodes the original particle index, scenes should call the bridge's sorted-key upload path instead of allocating a per-scene `sortedToOriginal` array. Ball Pit, Snakes, and Soft Body Blobs should expose its upload cost and active/uploaded/reserved rows in debug stats beside cell-range uploads.

`RawGpuConstraintParticleIndexMapGatherPass` consumes that index map and gathers solved sorted-state position/velocity texels into an original-order destination state. Use it only when the source sorted state and index map were produced from the same particle snapshot. This is the safe WebGL2-friendly alternative to scatter writes.

The gather pass must expose the order contract directly. Its stats report `sourceOrder: 'sorted-cell-key'`, `destinationOrder: 'original-index'`, whether position/velocity and attributes are preserved, and whether the gathered state is suitable for original-order feedback. Ball Pit and Snakes should report `liveGpuSortedCandidateGatherBackComplete`, `liveGpuSortedCandidateAuthoritativeReady`, and `liveGpuSortedCandidateAuthoritativeBlocker`. Authoritative readiness requires GPU-sorted candidate state, complete gather-back, complete candidate-slot consumption, and a spatially complete GPU broadphase. If any of those are false, the sorted path remains telemetry/stress only.

Ball Pit and Snakes may expose a guarded render feedback source from the gathered original-order sorted-candidate state, but only when the sorted state is GPU-owned, the gather-back is complete, all candidate slots are consumed, and the GPU broadphase reports authoritative suitability. Until those checks pass, rendering must use the CPU live state or CPU-fed texture bridge and report the blocker through debug stats. This keeps the visual bridge aligned with the eventual GPU-authoritative path without silently replacing the CPU collision or constraint solver too early.

Soft Body Blobs should use the same gather-back stats but split readiness into `gpuCandidateFeedbackReady` and `gpuCandidateAuthoritativeReady`. Feedback readiness can become true when contact, viscosity, and pressure slots are consumed and the solved sorted state gathers back to original order. When stress runs directly on original-index resident-list candidates, skip sorted-state gather-back and report `resident-list-original-order-stress-not-yet-feedback-owned` until the original-order stress result is explicitly allowed to feed rendering or CPU state. Authoritative readiness must remain false while body area preservation, body topology, and skin generation are still CPU-owned; report `body-area-and-skin-model-still-cpu-owned` rather than implying the GPU stress passes are the full soft-body engine.

Ball Pit, Snakes, and Soft Body Blobs own this gather pass through offscreen original-order destination states. Ball Pit and Snakes run it after sorted-copy collision telemetry; Soft Body Blobs run it after sorted-copy contact and viscosity telemetry. All three expose fragment cost before using gathered state for visible physics.

`RawGpuConstraintParticleViscosityPass` is the reusable velocity-relaxation companion to circle contact stress. It consumes the same neighbor-slot textures in bounded batches and should stay non-authoritative until the broadphase reports spatial completeness, every slot batch is consumed, and the remapped original-order state can safely replace or feed the CPU-owned body model.

`RawGpuConstraintParticlePressurePass` is the reusable body-aware local spacing primitive for soft bodies and thick chains. It reads body ids from particle attributes, can restrict relaxation to same-body neighbors, and should be treated as pressure/shape telemetry until a GPU-owned body-area or constraint graph state replaces the CPU body model.

`RawGpuConstraintParticleBodyMetadataBridge` uploads compact per-body center/rest-size data for body-aware passes. `RawGpuConstraintParticleBodyShapePass` consumes that metadata to apply a soft radial envelope in texture space. This is not a replacement for true area preservation; it is a reusable stepping stone that lets Snakes and Soft-Body Blobs measure GPU body-shape cost before a full GPU body-area reduction exists.

`RawGpuConstraintParticleCircleCollisionPass` supports `neighborSlotOffset` so scenes can consume large candidate-slot sets in batches without adding scene-specific shaders. Ball Pit uses this only as sampled stress on the separate sorted candidate copy. The live interactive simulation remains CPU-authoritative and the visible render bridge still solves against CPU-owned neighbor slots; the sorted-cell batched solve is telemetry proving that the generated resident slots can be consumed across multiple pass invocations.

Batched collision telemetry should compare aggregate consumed slots against generated candidate slots after all batches complete. Per-batch `ignoredNeighborSlotCount` means "not consumed by this invocation"; it does not mean the slots are lost if a later batch consumes them. Ball Pit reports expected slots, consumed slots, required batches, completed batches, and an aggregate consumption ratio for this reason.

`RawGpuConstraintParticleCellOccupancyPass` is the first GPU-owned broadphase replacement stepping stone. It rasterizes one point per particle into a world-cell occupancy texture using additive blending when supported. `RawGpuConstraintParticleCellOffsetPass` then runs a reusable GPU prefix sum over that occupancy texture to produce inclusive cell-end offsets. `RawGpuConstraintParticleCellRangeFromOffsetsPass` converts those offsets into `{start,end,count,active}` cell ranges that can feed the existing sorted candidate bridge without uploading CPU-built range textures. This proves GPU-resident occupancy, offset generation, and sorted-state range generation, but it still does not produce resident particle lists for an unsorted authoritative state. Ball Pit, Snakes, and Soft-Body Blobs should run these passes beside their sorted candidate bridge so occupancy cost, prefix cost, range-fragment cost, and avoided CPU cell-range upload cost can be compared on the same particle snapshot. Treat `producesResidentLists: false`, `sortedStateRequired: true`, and `suitableForAuthoritativeUnsortedBroadphase: false` as hard gates until a GPU particle-cell scatter pass exists.

`RawGpuConstraintParticleCellKeyPass` and `RawGpuKeyIndexSortPass` are the next GPU-owned broadphase step. The cell-key pass emits `{cellId, particleIndex, cellX, cellY}` for an unsorted particle texture. The key/index sorter performs a generic texture-backed bitonic sort over `{key,index}` texels. Together they are the intended replacement for CPU-side particle sorting before range/list derivation. Scene integrations should expose key-fragment cost, sort capacity, sort pass count, sort fragment cost, and whether the sorted output is feeding candidate generation. Do not remove the CPU sorted-copy fallback until sorted key output can derive resident ranges and preserve original-index gathers for live CPU-owned solvers.

Ball Pit, Snakes, and Soft-Body Blobs all run live telemetry integrations for `RawGpuConstraintParticleCellKeyPass` plus `RawGpuKeyIndexSortPass`. While the path is still sampled from the live sorted-candidate probe, its stats establish the sort cost envelope before using the sorted output as the source of candidate ranges. Keep the CPU sorted-copy bridge until sorted key output can derive resident ranges and original-index gathers without CPU ordering.

`RawGpuConstraintParticleSortedKeyRangePass` derives `{start,end,count,active}` cell ranges from a GPU-sorted key/index texture using per-cell binary search. Ball Pit, Snakes, and Soft-Body Blobs should prefer this range texture for candidate telemetry when available. This removes another CPU-owned broadphase step from the probe, but it still requires the particle state itself to be in the same order as the sorted keys before the path can become authoritative.

`RawGpuConstraintParticleResidentListFromSortedKeysPass` is the WebGL2-native replacement for a literal particle-cell scatter. Because WebGL2 does not expose compute-style storage buffers or image atomics, the pass consumes the GPU-sorted `{cellId, originalIndex}` texture and writes a packed resident-list texture `{originalIndex, cellId, residentSlot, active}` by binary-searching each cell. This produces GPU-owned resident lists without CPU range/list construction. It is suitable for candidate generation when the resident limit is nonzero, and it is suitable for authoritative unsorted broadphase only when the resident limit covers the measured max cell occupancy. The next shared primitive should consume this resident-list texture directly to emit neighbor slots for Ball Pit, Snakes, and Soft-Body Blobs.

Ball Pit now runs the resident-list pass as live sorted-candidate telemetry after GPU key sorting and range derivation. Its debug stats should expose resident-list texture dimensions, fragment cost, resident limit, max cell occupancy, candidate readiness, and authoritative readiness. This stage still does not replace candidate generation until a resident-list candidate-slot pass consumes the packed resident texture directly.

`RawGpuConstraintParticleResidentListCandidatePass` consumes the packed resident-list texture and emits neighbor-slot textures in original particle-index order. This is the first fully GPU-owned unsorted broadphase candidate path: grid keys, key sorting, resident lists, and candidate slots can all be generated without CPU resident-list construction. Ball Pit, Snakes, and Soft Body Blobs run this pass as parallel live telemetry while the existing sorted-cell candidate stress path remains isolated from visible physics. Do not feed resident-list candidate slots into the sorted-state collision stress solver; they are original-index slots intended for the CPU-fed/original-order live texture bridge and later a GPU-authoritative original-order solver.

Ball Pit, Snakes, and Soft-Body Blobs may consume resident-list candidate slots for the visible live GPU collision bridge when `RawGpuConstraintParticleResidentListCandidatePass` reports original-index order and authoritative broadphase coverage on the current sampled frame. This skips the CPU spatial-neighbor slot upload for that frame, but it is still a render-bridge collision stage while the CPU engine owns canonical positions, topology, and body state. Report this as `gpu-resident-list-live-render-collision`, not as a fully GPU-authoritative simulation, until the CPU engine state is replaced or fed back safely.

Spatial-neighbor bridge telemetry must expose the upload source as well as the skip boolean. Ball Pit reports `liveGpuSpatialNeighborUploadSource`; Snakes and Soft-Body Blobs report `liveGpuCollisionNeighborUploadSource`. Valid values are `cpu-spatial-neighbor-slots`, `gpu-resident-list`, and `none`. `gpu-resident-list` is the only source that should count as CPU spatial-neighbor upload elimination; `none` means no usable bridge was present, not a successful GPU replacement.

Ball Pit may also run `RawGpuConstraintParticleStepPass` on the CPU-seeded live texture bridge as a `cpu-seeded-gpu-step-probe`. This proves the shared position/velocity integrator can advance the live particle texture and exposes fragment cost, active rows, particle count, and `liveGpuStepAuthoritativeReady: false`. Do not count this as CPU upload elimination: the CPU still seeds the state each frame, and the next migration step is allowing the GPU-owned state to persist across frames while CPU input/spawn commands patch only changed particles.

Ball Pit can now gate that same step pass into a `persistent-gpu-step-probe` when the particle count is stable, static attributes are clean, the GPU state has already been seeded, and no pointer input is active. In that mode the dynamic CPU position upload is skipped for the frame and debug stats must expose `liveGpuDynamicUploadSkipped` plus `liveGpuDynamicUploadSkipBlocker`. This is still not authoritative simulation because CPU topology, spawning, removal, and collision ownership remain live; the value of the probe is measuring how often the scene can preserve GPU position/velocity state before the final CPU-state handoff.

On `persistent-gpu-step-probe` frames, Ball Pit should run the GPU step before refreshing sorted/resident-list broadphase telemetry, force that telemetry refresh with `liveGpuSortedCandidateRefreshReason: 'persistent-gpu-frame'`, and label `liveGpuSortedCandidateSource: 'persistent-gpu-live-state'`. That makes resident-list candidate stats reflect the post-step GPU texture instead of a stale CPU-seeded snapshot. Keep `liveGpuStepAuthoritativeReady: false` until collision, spawning, removal, and CPU feedback are all handed off.

Ball Pit live debug stats should split the old broad `cpuUpload` flag into actionable migration buckets. `liveGpuDynamicCpuUploadEliminated` proves the hot position upload was skipped; `liveGpuRemainingCpuBridgeUploadFloats`, `liveGpuRecurringCpuBridgeUploadFloats`, `liveGpuSeedCpuBridgeUploadFloats`, and `liveGpuRemainingCpuBridgeBlocker` identify the next CPU bridge still in the path, such as CPU spatial-neighbor slots, CPU sorted-candidate copies, cell-range bridge uploads, or index-map bridge uploads. Optimization decisions should prioritize recurring bridge upload cost; seed/static upload cost is still useful for reset/topology churn but should not be treated as a steady-state hot-path bottleneck. This keeps optimization work focused on the remaining CPU-owned bridge rather than treating every GPU-rendered frame as equally migrated.

Ball Pit, Snakes, and Soft-Body Blobs should report `liveGpuSortedCandidateCellRangeSource` beside `liveGpuSortedCandidateCellRangeUploadFloats`. The preferred source order is `gpu-sorted-key-range`, then `gpu-occupancy-offset-range`, then `cpu-cell-range-bridge`. A frame using either GPU range source must keep cell-range upload floats at zero; any nonzero cell-range bridge upload is a migration blocker and should show up through `liveGpuRemainingCpuBridgeBlocker: 'cpu-cell-range-bridge'`.

`RawGpuConstraintParticleSortedKeyGatherPass` gathers an original-order particle texture into sorted-cell-key order using the sorted key/index texture. It gathers position, velocity, and attributes so radius, inverse-mass, body id, and original-index metadata stay aligned with the sorted state. Ball Pit and Snakes use this as the first GPU-generated sorted particle state probe. Soft-Body Blobs own a separate original-order GPU source and sorted candidate destination so their candidate state can now be generated by GPU gather instead of CPU sorted packing. Candidate generation may consume this gathered sorted state plus `RawGpuConstraintParticleSortedKeyRangePass` output, but the old CPU sorted-copy upload should remain visible in telemetry until it is explicitly removed and the gather path is proven to preserve collision/gather-back behavior.

Ball Pit and Snakes should report `liveGpuSortedCandidateUploadMode`; Soft-Body Blobs should report `gpuCandidateUploadMode`. `gpu-sorted-key-gather` means the sorted candidate state was produced by GPU key/sort/gather and the CPU sorted-position texture upload was skipped. `cpu-sorted-copy` means the fallback CPU sorted-position upload is still active. Keeping this distinction visible is required while the CPU index-map and gather-back scaffolding still exist. The shared index-map bridge must upload only active texture rows, plus any previously active rows that need clearing after shrink. Debug stats should expose index-map active rows, uploaded rows, reserved rows, and upload floats so scenes can prove they are not clearing/uploading reserved candidate capacity.

Index-map bridge uploads should only run when the sorted candidate state is GPU-owned (`gpu-sorted-key-gather`). If the scene is still using `cpu-sorted-copy`, gather-back cannot prove GPU ownership, so the index map should report `liveGpuSortedCandidateIndexMapSource: 'skipped-non-gpu-sorted-state'` with zero upload floats. Gather-back passes must only consume the index-map framebuffer when the current frame reports `cpu-index-map-bridge`; this prevents stale remap textures from making telemetry look more authoritative than the current frame actually is. The eventual replacement is a GPU-derived original-index remap texture, but until that exists the CPU bridge should be limited to frames where it can directly advance feedback-readiness.

Dense collision scenes should report occupancy point draws, occupancy cell count, additive-blend support, cell-offset prefix passes, cell-offset fragment cost, GPU cell-range fragment cost, CPU cell-range upload floats, and candidate-slot fragment cost together. The next migration stage is justified only when that telemetry shows the CPU range bridge is eliminated or no longer the bottleneck and the GPU occupancy/offset/range textures have stable coverage at the target grid resolution.

GPU circle-collision backends must expose whether they are spatially complete. Scenes must not switch authoritative collision from CPU to GPU unless the backend reports a world-space broadphase/tiled-neighborhood strategy suitable for authoritative collision. Texture-adjacency passes are useful scaffolds and stress probes, not production dense collision solvers. CPU-seeded spatial neighbor slots are a better render bridge and stress path, but still not fully GPU-authoritative because the broadphase remains CPU-owned and bounded by slot capacity.

Spatially seeded GPU preview/demo clouds may arrange initial particle texture order so adjacent texels correspond to adjacent world-space particles. This makes `gpu-grid-key-window` a better stress probe without adding CPU candidate uploads. Do not apply this reordering to live CPU-indexed render bridges unless the scene uses a separate sorted GPU state; CPU-seeded neighbor slots refer to CPU particle indices and would point at the wrong particles if the shared live state were reordered in place.

Live CPU-indexed bridges may create a separate sorted GPU candidate state for telemetry. Ball Pit uses this pattern so the render/collision bridge can keep CPU particle order for CPU-owned neighbor slots while a second texture state is sorted by world grid cell and fed through `RawGpuConstraintParticleGridKeyPass` plus `RawGpuConstraintParticleCandidateSlotPass`. This adds one extra dynamic position upload and memory copy, so it is a migration probe rather than the final architecture. The final path should make the GPU state authoritative and remove the duplicated CPU-indexed upload.

Dense particle live telemetry must compare CPU spatial candidate workload against GPU candidate-slot capacity before any authoritative migration. Ball Pit, Snakes, and Soft-Body Blobs should all track CPU slot writes, CPU candidate pairs, GPU candidate capacity, GPU candidate fragment cost, and a coverage status. A GPU path is not eligible for authoritative collision merely because capacity exceeds CPU slot writes; it must also report spatial completeness from the GPU backend.

CPU-seeded spatial collision slots must report staging work separately from texture upload work. `AdvancedCollisionStressEngine.writeCircleParticleSpatialNeighborSlots` and `AdvancedCircleParticleEngine.writeSpatialCollisionNeighborSlots` expose `stagingClearFloats` and `stagingWriteFloats`; scenes should display those beside slot writes, candidate pairs, and `RawGpuConstraintParticleNeighborSlots` upload rows/floats. A live GPU bridge is only getting cheaper when the CPU broadphase, CPU staging clears, GPU upload rows, and GPU solve fragments all move down together. Typed-array bulk clears are preferred over per-float JavaScript clears, but this is still CPU-owned broadphase work until a spatially complete GPU candidate backend replaces it.

Ball Pit preview/demo modes may run non-authoritative GPU collision stress passes to exercise shared texture-state plumbing, active-row fragment cost, and renderer consumption from post-pass textures. These modes must label themselves as stress/demo paths and keep live gameplay collision CPU-authoritative until the GPU backend exposes a spatially complete broadphase.

Snakes and Soft-Body Blob preview/demo modes may use the same non-authoritative circle-collision stress pass after GPU distance-constraint relaxation and before density/metaball rendering. Those modes should expose whether a frame was CPU-seeded or resident via `gpuConstraintStepSource`, `liveGpuDynamicUploadSkipped`, and `liveGpuDynamicUploadSkipBlocker`. Snakes and Soft-Body Blobs may also share `RawGpuConstraintParticlePressurePass` as a thick-body local spacing probe over the sorted candidate copy. Autonomous GPU previews should not consume CPU-position spatial slots after the GPU state starts moving; use texture-layout stress collision there until a GPU-owned candidate generator exists. CPU-backed live render bridges may use CPU-seeded spatial collision candidate slots because the uploaded positions and CPU broadphase agree for that frame.

Ball Pit, Snakes, and Soft-Body Blobs should all run `RawGpuConstraintParticleGridKeyPass` before GPU candidate-slot generation so broadphase telemetry remains comparable across scenes. Their preview/demo stress paths may consume `RawGpuConstraintParticleCandidateSlotPass` output, but live authoritative behavior must keep `gpuCollisionAuthoritativeReady: false` until GPU candidate slots are generated by a spatially complete backend with overflow/completeness telemetry.

Live candidate telemetry should be sampled instead of run as a mandatory per-frame hot-path pass while collision is still CPU-authoritative. Ball Pit keeps a separate sorted GPU candidate copy for broadphase probes, while Snakes and Soft-Body Blobs keep live density rendering on the texture bridge every enhanced frame. In both cases, grid-key/candidate-slot telemetry can refresh on topology/count edits or a short cadence. Debug stats must expose whether the candidate data was sampled this frame, how stale it is, and whether the live probe is a sorted copy or a CPU-indexed unsorted texture bridge.

Vascular-style growth scenes are field-first GPU candidates. Sparse branch topology may remain CPU-owned while the branch influence field lives persistently on the GPU and feeds back through bounded tip sampling. Sampling passes should be skipped when there are no active tips, and debug stats should separate resident field pixels, field draw counts, sample upload/readback cost, and whether GPU field feedback was active on the current frame. The final GPU-native version should move growth probability and tip advancement into texture passes; until then, `gpuSimulated` should remain false even though growth is GPU-assisted.

`RawGpuConstraintParticleNeighborSlots` owns those bounded neighbor-slot textures and handles one-time or topology-edit seed uploads. Do not upload these every frame; update them only when particles or constraints are created, removed, or rebuilt.

Texture channel convention:

- Position state: `xy` current position, `z` radius, `w` group or body id.
- Velocity state: `xy` velocity or Verlet delta, `z` inverse mass, `w` flags.
- Attribute state: `x` radius, `y` inverse mass, `z` local id, `w` seed or material id.
- Constraint state: `x` particle A, `y` particle B, `z` rest length, `w` stiffness.
- Neighbor-slot state: `x` neighbor particle index, `y` rest length/contact radius, `z` stiffness/contact weight, `w` enabled flag.
- Distance-constraint passes interpret neighbor slots as persistent topology constraints. Circle-collision passes interpret the same slot layout as bounded collision candidates. Debug stats must expose broadphase owner (`texture-layout`, `cpu`, and eventually `gpu`) so CPU-seeded candidate slots are not mistaken for a GPU-owned broadphase.

## Vascular GPU field migration

`RawGpuInstancedSegmentField` rasterizes packed segment topology into a GPU-resident field texture. Use it for Vascular-style sparse branching simulations when branch energy, coverage, or nutrient feedback needs to move out of CPU-only arrays. The field supports GPU-side persistence by decaying the previous field texture through a fullscreen feedback pass before injecting the current branch raster. It also owns bounded GPU-side field impulses for pointer tools such as guide/feed/prune; scenes should call the shared impulse API and report impulse count/pixel telemetry rather than adding scene-local hidden field passes. `RawGpuTexturePointSampler` can sample a small set of world-space points from that field into a tiny readback strip; this is acceptable for sparse feedback loops, but full-field readbacks are not. The initial Vascular integration keeps topology CPU-owned while allowing active growth tips to consume sparse GPU-derived field feedback, with explicit debug stats (`branchFieldResident`, additive blend support, persistent feedback, dimensions, fragment pixels, feedback pixels, impulse pixels, sample count, sample readback floats, upload floats, draw count). The renderer accumulates into float textures only when `floatBlend` is supported; otherwise it still maintains a compatibility field texture without additive injection. Do not label Vascular as fully GPU-simulated until growth/topology creation itself lives in GPU state instead of CPU node arrays.

The Vascular `resolution` setting controls the target GPU field texture resolution, not canvas pixel ratio. Scene code should derive field scale from that setting and report both the requested target and actual field texture dimensions. Feedback sampling should scale with requested field resolution under a bounded cap so high-resolution runs get useful GPU feedback without turning preview tiles into readback stress tests.

Active-tip feedback sampling should rotate its sample window across frames instead of repeatedly sampling the same stride phase. Keep the upload/readback strip bounded, but expose sample start, stride, coverage, upload floats, readback floats, and fragment pixels so higher-resolution Vascular runs can prove they are improving feedback coverage over time without increasing per-frame CPU/GPU transfer size.

When a Vascular scene applies sampled field feedback, the sampled values must be mapped back to the exact active-tip indices that produced the sample points. Rotating the point window but applying samples to a fresh non-rotated stride silently corrupts the feedback loop and weakens any CPU-throttle decision based on field energy. Idle draw skips should also preserve the last useful feedback energy/status rather than resetting it to inactive, because that retained GPU field signal is what allows the next frame to avoid unnecessary saturated CPU work.

When Vascular topology is saturated and there is no active pointer interaction, strong GPU field feedback may throttle short CPU growth/style update slices. This throttle may be adaptive: stronger feedback and higher requested field resolution can extend the skip window, but the window must stay bounded and visible in debug stats. This is a GPU-assisted CPU-work reduction, not GPU simulation: topology remains CPU-owned, but the GPU-resident field controls whether the CPU model needs to advance every host frame. Debug stats should expose skipped CPU updates, throttle seconds, throttle window, skip counts, avoided CPU update seconds/frames, feedback-assisted frames, useful versus weak feedback frames, active-tip sample coverage, sampler upload/readback totals, readback floats per avoided CPU second, and effective CPU update dt so responsiveness regressions and readback-cost regressions are visible.

When the saturated Vascular model does run a CPU update under useful GPU feedback, it should also shrink the style-scan chunk before falling back to a full saturated scan. Preserve elapsed time by scaling the scan's effective dt over the reduced chunk, and expose `styleScanBudgetScale`, `styleScanAvoidedCount`, and cumulative avoided scan nodes. This gives the GPU field two levels of CPU reduction: full short-update skips while the feedback throttle window is active, and smaller style maintenance scans when the CPU catches up.

The raw host render gate may also use the same bounded GPU feedback signal after topology saturation. Strong field feedback can lengthen the idle render interval so the scene avoids waking only to redraw unchanged branches or repeat tiny readbacks. Expose `vascularGpuFeedbackHostFrameInterval` and `vascularGpuFeedbackHostGateReason` so this remains auditable, and always bypass the gate for pointer input, resize, reset, settings/style changes, or unsaturated growth.

## Avoid

- Per-frame `texSubImage2D` field uploads for dense grids.
- Per-frame object allocation in solver or renderer hot loops.
- Per-frame CPU topology/stat polling inside GPU preview loops after topology has already been seeded.
- Recomputing preview stats every frame for texture-backed demos with static topology; cache stats at seed/reseed time instead.
- `.subarray()` allocations for active upload ranges.
- Public exports of legacy CPU-upload scenes when a GPU-native scene exists.
